1. Overview & Design Goals

The toolkit provides a safe, reversible mechanism for applying firmware modifications to Hasselblad X System cameras. Every modification is wrapped in a journal transaction that records exactly what changed, backs up every replaced file, and can restore the camera to its original state at any time.

Design principles:

  • Offline-first — all planning, validation, and dry-run operations work on a desktop against firmware profiles. No camera contact unless explicitly executing an install or restore.
  • Atomic writes — every file operation uses write-to-tmp + os.replace(). A crash at any point leaves either the old file or the new file, never a half-written one.
  • SHA-256 at every step — before-and-after hashes for every file. Restore verifies the current hash matches the expected modded hash before overwriting. Tamper detection is immediate.
  • A/B slot awareness — the journal knows which boot slot was active when mods were installed and refuses to operate if slots have been swapped (e.g., by an official firmware update).
  • LIFO restore ordering — if mod B modifies a file that mod A already touched, mod B must be restored before mod A. This is enforced, not advisory.
  • Self-describing manifests — schema version in every manifest so any version of the engine can read any journal.

2. A/B Partition Scheme

X System cameras run a modified Android system with an A/B partition layout. Two complete system slots exist; one is active, one is inactive. Official firmware updates write the inactive slot and flip on reboot.

On-camera utilities

UtilityPurposeKey arguments
/sbin/unrd Read/write boot slot status in non-volatile storage unrd <key> to read, unrd <key> <value> to write
boot_control Mark slot as bootable / successful boot_control -m to mark current slot

Key unrd properties

KeyValuesMeaning
slot_N.status_active 0 / 1 Whether slot N is the active boot target. Exactly one slot should be 1.
crash_counter integer string Boot failure tracking. If set (even to "0"), the system is in a verified-boot cycle. Journal refuses all operations.
hbl_upgrading slot number string Firmware upgrade in progress to this slot. Journal refuses all operations.

Why mods write the active slot only

Official updates write the inactive slot then flip. Mods do the opposite: they write the active slot only. This means:

  • An official update after modding writes a clean image to the inactive slot and flips to it — mods are automatically left behind, not carried forward.
  • If something goes wrong, the inactive slot still has clean stock firmware. The emergency slot restore flips back to it.
  • The journal records which slot was active at install time and blocks operations if the slot has changed.

SlotInfo data structure

@dataclass
class SlotInfo:
    active: int | None = None       # 1 or 2
    inactive: int | None = None     # the other one
    crash_counter: str | None = None
    hbl_upgrading: str | None = None

Populated by parsing the output of /sbin/unrd for slot_1.status_active, slot_2.status_active, crash_counter, and hbl_upgrading. When None (desktop testing without a camera), slot safety checks are skipped.

3. Journal Lifecycle & Phases

A journal progresses through a strict phase state machine. The phase is stored in the manifest and checked on every operation.

(no journal) → PREPARED → INSTALLED → RESTORING → RESTORED
(no journal) → PREPARED → INSTALLED → FAILED ← (slot restore)
PhaseMeaningAllowed operations
PREPARED Manifest created, backups written, but mod files not yet copied to system. Indicates a possible interrupted install. Install (resume or new), verify
INSTALLED One or more mods are active on the system. Install more mods, restore (individual or all), verify, export, snapshot
RESTORING A restore is in progress. No installs allowed. Restore (continue/retry), verify
RESTORED All mods successfully restored. System matches stock. Fresh install cycle, verify
FAILED Emergency slot restore was performed. Mods on the old slot are abandoned. Read-only. Manual intervention needed.

4. Manifest Schema (v4)

The journal manifest is a self-describing JSON file at /blackbox/modjournal/manifest.json on the camera (or at any local path for desktop testing).

{
  "schema": "hasselblad-mod-journal-v4",
  "phase": "installed",
  "firmware_sha256": "8c5af67c...the firmware file hash",
  "profile_version": "X2DII_100C_v1_3_18_1",
  "active_slot": 1,
  "inactive_slot": 2,
  "created": 1729900000.0,
  "updated": 1729900123.0,
  "entries": [
    {
      "path": "/system/bin/camera-gui-software",
      "action": "replaced",
      "hash_before": "8c5af67c...stock SHA-256",
      "hash_after": "07f4d058...modded SHA-256",
      "backup_path": "video-mode-restore__system__bin__camera-gui-software",
      "mod_id": "video-mode-restore",
      "timestamp": 1729900100.0
    }
  ]
}

JournalEntry fields

FieldTypeDescription
pathstringAbsolute path on the camera filesystem
action"replaced" | "created"Whether the file existed before (replaced) or is new (created)
hash_beforestring | nullSHA-256 of the file before modification. null for created files.
hash_afterstringSHA-256 of the installed mod file
backup_pathstring | nullFilename in backups/ directory. null for created files (nothing to back up).
mod_idstringWhich mod this entry belongs to

Action enum semantics

ActionInstall behaviorRestore behavior

5. Install Flow

The install sequence for Journal.install_mod(mod_id, files):

  1. Pre-flight checks
    • Load existing manifest (or create new one)
    • Reject if phase is RESTORING (mid-restore, cannot install)
    • Reject if mod_id already has entries (must uninstall first)
    • Run _check_slot_safety(): reject if hbl_upgrading is set, if crash_counter is set, or if active slot differs from the slot recorded in the manifest
  2. Set phase to PREPARED and write manifest (crash-safe checkpoint)
  3. For each file in the mod:
    • If the file exists on the system:
      • Compute SHA-256 of the current file (hash_before)
      • Atomic-copy it to backups/{mod_id}__{sanitized_path}
      • Create entry with action REPLACED
    • If the file does not exist:
      • Create parent directories
      • Create entry with action CREATED, hash_before=None, backup_path=None
    • Atomic-copy the mod file to the system path
    • Compute SHA-256 of the installed file (hash_after)
    • Record overlap warnings if this file was touched by another mod
  4. Set phase to INSTALLED, record active_slot and inactive_slot, write manifest

Atomic file operations

def atomic_copy(src: Path, dst: Path) -> None:
    """Copy src to dst via a temporary file + os.replace().
    If we crash mid-write, the temp file is orphaned but
    dst is never left in a partial state."""
    tmp = dst.with_suffix(dst.suffix + ".tmp")
    shutil.copy2(src, tmp)
    os.replace(tmp, dst)

def atomic_write_json(path: Path, data: dict) -> None:
    """Write JSON atomically."""
    tmp = path.with_suffix(".tmp")
    tmp.write_text(json.dumps(data, indent=2), encoding="utf-8")
    os.replace(tmp, path)

6. Restore Flow & LIFO Ordering

Single-mod restore: Journal.restore_mod(mod_id)

  1. LIFO check — for every file this mod touches, check if any later mod (installed after this one) also touches it. If so, that mod must be restored first. This prevents restoring an earlier backup over a later mod's changes.
  2. Slot safety — reject if active slot has changed since install.
  3. Set phase to RESTORING
  4. For each entry belonging to this mod:
    • If action was REPLACED:
      • Compute SHA-256 of the current file
      • Verify it matches hash_after — if not, the file was modified outside the journal and restore is blocked (tamper detection)
      • Atomic-copy the backup file back to the system path
    • If action was CREATED:
      • Delete the file
      • Remove empty parent directories
  5. Remove this mod's entries from the manifest
  6. Set phase to RESTORED (if no entries remain) or INSTALLED (if other mods still active)

Restore-all: Journal.restore_all()

Restores all mods in reverse installation order. This inherently satisfies LIFO constraints because it processes the most-recently-installed mod first.

LIFO example

Scenario: Two mods, one overlapping file Mod A replaces /system/bin/camera-gui-software (backs up stock). Then mod B replaces the same file (backs up mod A's version). Mod B's backup is mod A's file, not stock.

To get back to stock, you must restore B first (puts mod A's version back), then restore A (puts stock back). Restoring A first would overwrite B's changes with stock, losing the ability to cleanly undo B.

The journal enforces this: restore_mod("mod-a") raises RuntimeError citing mod-b as a blocker.

7. Emergency Slot Restore

When normal restore isn't possible (corrupted files, tampered state), the emergency slot restore abandons the modded slot entirely and boots into the clean inactive slot.

Pre-flight: Journal.preflight_slot_restore()

Returns a dict with viable (bool), issues (list), steps (planned actions), and slot information. Checks:

  • Slot info must be available (must run on the camera)
  • hbl_upgrading must not be set
  • crash_counter must not be set

Execution: Journal.slot_restore(dry_run=False)

The slot flip writes four values in sequence:

# 1. Reset crash counter (required before slot changes)
write_unrd("crash_counter", "0")

# 2. Activate the inactive slot
write_unrd("slot_2.status_active", "1")   # activate target

# 3. Deactivate the current slot
write_unrd("slot_1.status_active", "0")   # deactivate current

# 4. Mark the new slot as bootable
run_boot_control("-m")

After execution:

  • Journal phase is set to FAILED (the mods on the old slot are abandoned)
  • The camera must be rebooted to complete the restore
  • After reboot, the camera runs stock firmware from the other slot
Slot restore is a one-way operation The journal on the old slot is marked FAILED and cannot be used for further operations. The modded files still exist on the old slot's partition but are no longer active. A future official firmware update will overwrite them.

8. Stock Profiles

A StockProfile is a JSON file containing the SHA-256 hash, size, permissions, and SELinux context of every file in a stock firmware image. It serves as the ground truth for "what is stock?"

{
  "firmware": {
    "file": "X2DII_100C_1_3_18_1.hif",
    "sha256": "8c5af67c...",
    "build": "1.3.18.1",
    "product": "X2D II 100C"
  },
  "partitions": {
    "system": {
      "entries": [
        {
          "type": "file",
          "path": "/bin/camera-gui-software",
          "sha256": "...",
          "size": 23456789,
          "mode": "0755",
          "selinux": "u:object_r:system_file:s0"
        }
      ]
    }
  }
}

The StockProfile class provides:

  • stock_hash(path) — SHA-256 of a file in stock firmware
  • has_file(path) — whether a path exists in stock
  • Automatic path normalization (strips /system, /vendor, /blackbox prefixes)

9. Mod Manifests & Validation

Each mod is described by a JSON manifest (e.g., mods/video-mode-restore.json) that declares its target models, firmware versions, technique, files, and safety assessment. The mod_install.py tool validates these against a stock profile before any install attempt.

mod_install.py plan <mod.json> <profile.json> generates a dry-run install plan showing every operation, its risk level, and the journal entries that would be created — all without touching any files.

The hbjournal.py CLI wraps the journal engine for command-line use:

CommandCamera?Description

health <journal> <profile> Yes Pre-flight slot check (reads unrd)

*verify needs the system root to check file hashes — can be a mounted image or the live camera filesystem.

13. Extending the System

Adding a new mod

  1. Create a JSON manifest in mods/ with mod_id, target models/firmware, technique, files, and safety assessment
  2. Validate with python tools/mod_install.py validate mods/your-mod.json profiles/X2DII_100C_v1_3_18_1.json
  3. The journal engine handles the rest — backup, install, hash tracking, and restore

Supporting a new camera model

  1. Extract the firmware and build a stock profile (same JSON schema)
  2. Existing mods can declare the new model in target_models and add porting status
  3. The journal engine is model-agnostic — it works against any stock profile

Porting to a new firmware version

  1. Build a new stock profile for the firmware
  2. Run mod_install.py validate against it — hash mismatches will reveal which binaries changed
  3. For binary patches (like video-mode-restore): re-locate the function addresses in the new binary, verify the instruction sequences match, update the mod manifest
  4. For text-based mods (awk transforms, config edits): usually just adding the new firmware version hash to the manifest

Integration points for GUI/orchestration

The journal engine is a pure Python library with no UI dependencies. The Journal class is the primary interface:

from journal import Journal, StockProfile, read_slot_info

profile = StockProfile(Path("profiles/X2DII_100C_v1_3_18_1.json"))
slot_info = read_slot_info()  # on camera only

j = Journal(
    journal_dir=Path("/blackbox/modjournal"),
    system_root=Path("/system"),
    stock_profile=profile,
    slot_info=slot_info,
)

# Install
manifest = j.install_mod("video-mode-restore", {
    "/system/bin/camera-gui-software": Path("patched-binary"),
})

# Verify
issues = j.verify()

# Restore one mod
j.restore_mod("video-mode-restore")

# Or restore all
j.restore_all()

# Emergency: flip to clean slot
result = j.slot_restore(dry_run=False)
Key takeaway for implementers The journal is the single source of truth for system state. Every file operation goes through it. Every restore is verified against SHA-256 hashes. The A/B slot scheme provides a nuclear option when all else fails. Build on top of these primitives — don't work around them.
