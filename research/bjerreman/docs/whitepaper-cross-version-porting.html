1. The X System Landscape

The toolkit maintains stock profiles for every firmware version we've analyzed. These span four camera families across many firmware generations:

Camera Profiles Firmware range Platform
X1D 50C 6 v1.20.0 – v1.25.0 Android, ARM64
X1D II 50C 7 v1.0.1 – v1.5.2 Android, ARM64
X2D 100C 11 v1.0.5 – v4.2.0 Android, ARM64
X2D II 100C 7 v1.1.8.6 – v1.3.18.1 Android, ARM64

All four share the same base platform (Android on ARM64) and the same GUI binary (camera-gui-software), but the binaries diverge significantly between models and even between major firmware versions within a model. Minor version bumps (e.g., 1.3.16.2 to 1.3.18.1 on X2D II) tend to preserve function addresses and instruction sequences.

2. Stock Profiles as the Comparison Baseline

A stock profile contains the SHA-256 hash, size, permissions, and SELinux context of every file in a firmware image. Two profiles can be compared to answer three questions:

  1. Did a specific file change? — Compare its SHA-256 across versions. Identical hash = identical file = mod applies without changes.
  2. Does the target file exist? — A mod for a file that doesn't exist in the target firmware needs a different approach or isn't applicable.
  3. Did surrounding files change? — Even if the target file is identical, changes in files it depends on (libraries, configs, QML imports) may affect behavior.

Profile comparison with the toolkit

# Compare a specific file across two firmware versions
from mod_install import FirmwareProfile

profile_a = FirmwareProfile(Path("profiles/X2DII_100C_v1_3_16_2.json"))
profile_b = FirmwareProfile(Path("profiles/X2DII_100C_v1_3_18_1.json"))

path = "/bin/camera-gui-software"

hash_a = profile_a.stock_hash(path)
hash_b = profile_b.stock_hash(path)

if hash_a == hash_b:
    print("Identical binary — mod applies as-is")
elif hash_a and hash_b:
    print("Binary changed — re-analysis needed")
elif hash_b is None:
    print("File removed in target firmware")
else:
    print("File added in target firmware")

Batch profile diffing

# Find all files that changed between two versions
def diff_profiles(a: FirmwareProfile, b: FirmwareProfile) -> dict:
    all_paths = set(a._entries) | set(b._entries)
    changed, added, removed = [], [], []
    for p in sorted(all_paths):
        ha, hb = a.stock_hash(p), b.stock_hash(p)
        if ha and hb and ha != hb:
            changed.append(p)
        elif ha and not hb:
            removed.append(p)
        elif not ha and hb:
            added.append(p)
    return {"changed": changed, "added": added, "removed": removed}

3. Mod Techniques & Their Portability

Different mod techniques have very different portability characteristics. Understanding this determines how much work a port requires.

Binary ELF Patch (code cave trampoline)

version-locked camera-gui-software

Modifies specific instruction offsets in the compiled binary. A function's address, instruction encoding, and epilogue layout must all match exactly. Any recompilation of the binary invalidates the patch.

Portability: Must re-locate every address when the binary changes. Same technique may work but offsets will differ. Within minor versions (e.g., 1.3.16.2 and 1.3.18.1), addresses are often identical.

Tools: elf_patcher.py (ELF analysis, code cave discovery, PLT parsing), llvm-objdump for disassembly verification.

Binary String Patch (same-length replacement)

semi-portable camera-gui-software

Replaces embedded strings (menu labels, about-page text) with same-length or shorter strings, null-padded to preserve all offsets. No instruction changes.

Portability: Portable across versions where the string exists at any offset. The BinaryPatcher.find_string() method locates strings dynamically. Breaks only if the string was removed or reworded.

Tools: binary_patcher.py (string search, safe replacement, QML block analysis).

Text/Config Transform (awk, sed, init scripts)

portable *.rc, *.conf, *.qml

Modifies text configuration files or init scripts. Transforms are specified as patterns (find line X, change to Y) rather than absolute offsets.

Portability: Highly portable. Patterns match across versions as long as the target file's structure is preserved. Validate by checking that the expected pattern exists in the new version.

dlsym Interposition (LD_PRELOAD)

semi-portable custom .so

Loads a custom shared library that intercepts function calls via LD_PRELOAD. No modifications to existing binaries.

Portability: Survives minor updates as long as the intercepted symbol names and calling conventions haven't changed. Verify symbol existence with nm or the ELF analyzer's PLT parser.

4. Binary Patch Porting (Step by Step)

When a binary patch's target binary has changed (different SHA-256), here's the systematic process to port it:

1 Compare binaries at profile level

python tools/mod_install.py validate mods/your-mod.json profiles/NEW_PROFILE.json

This immediately tells you whether the stock hashes match. A hash mismatch on the target binary means the patch must be re-derived.

2 Locate the target function in the new binary

For named C++ symbols, search by the mangled name:

# Find the camera_capabilities getter in the new binary
$(xcrun -f llvm-objdump) --syms new-binary | grep camera_capabilities

# Or disassemble around the known symbol
$(xcrun -f llvm-objdump) --triple=aarch64 -d \
  --start-address=0xSOME_ADDR --stop-address=0xSOME_ADDR+0x40 \
  new-binary

For stripped binaries without symbols, use pattern matching on the instruction sequence:

# Search for the known instruction pattern of the getter epilogue
# (LDR X19, [SP, #16] ; LDP X29, X30, [SP], #32 ; RET)
# Hex: F3 0B 40 F9  FD 7B C2 A8  C0 03 5F D6
python -c "
import sys
data = open(sys.argv[1], 'rb').read()
pattern = bytes.fromhex('f30b40f9fd7bc2a8c0035fd6')
off = 0
while True:
    off = data.find(pattern, off)
    if off < 0: break
    print(f'  0x{off:08x}')
    off += 1
" new-binary

3 Find a code cave in the new binary

# Use the ELF analyzer to find usable zero-filled regions
python tools/elf_patcher.py new-binary --json | python -m json.tool

The analyzer finds inter-section gaps and runs of zero bytes within .text, ranked by size. Pick a cave that's large enough for your trampoline and in range of a B instruction (128 MB for unconditional branch).

4 Verify the instruction context

Disassemble a window around the located function to verify the instruction sequence matches what the patch expects. The patch must:

  • Replace the exact instruction at the redirect offset
  • The trampoline must reproduce any instructions it displaced
  • Register usage must match (the trampoline saves/restores the same registers)

5 Recompute branch offsets

# ARM64 B instruction encoding
from elf_patcher import arm64_branch

redirect_addr = 0x_NEW_GETTER_EPILOGUE
cave_addr = 0x_NEW_CAVE

branch_bytes = arm64_branch(redirect_addr, cave_addr)
print(f"Redirect instruction: {branch_bytes.hex()}")

6 Update the mod manifest

Add the new firmware version entry with updated offsets, hashes, and instruction bytes. Keep the old version entry — mods can support multiple firmware versions simultaneously.

7 Validate with the toolkit

python tools/mod_install.py validate mods/updated-mod.json profiles/NEW_PROFILE.json

Then optionally verify in QEMU if a DevKit image is available for that firmware.

5. Text & Config Mod Porting

Text-based mods are simpler to port because they operate on patterns, not offsets:

Verification checklist

  1. File exists? — profile.has_file(path)
  2. File hash changed? — compare profile.stock_hash(path) across versions
  3. Pattern still matches? — if hash changed, extract the file from the new firmware and check if the awk/sed pattern still hits
  4. Update stock_sha256 in manifest — even if the pattern matches, the new version's hash must be recorded for journal integrity
Hash changed but pattern matches? This is the most common case for text mods across minor versions. A config file gets a new option or comment, but the lines your mod targets are unchanged. Update the stock hash in the manifest and you're done.

6. Cross-Model Feasibility Analysis

Porting between camera models (e.g., X2D II to X2D, or X2D to X1D II) is fundamentally different from porting between firmware versions of the same model. The binary is recompiled for each model, and feature sets diverge.

Feasibility tiers

Tier Meaning Example
IDENTICAL_PATCH Same offsets, same instructions, same cave. Applies byte-for-byte. Video restore across X2D II 1.3.16.2 and 1.3.18.1
SAME_TECHNIQUE Same function exists, same approach works, but offsets differ. Requires re-derivation. About-page string mod across firmware major versions
PARTIAL_PORT Some components exist in the target model, others are missing. Mod scope must be reduced. BT enhancements: shared infrastructure, minor differences
NOT_FEASIBLE Target lacks required hardware/firmware infrastructure entirely. Object detection AF on X2D (requires ML hardware absent from X2D)
NOT_APPLICABLE Feature gate doesn't exist in the target model's binary. Video mode on X2D (no E_CameraMode_Video enum)

How to determine feasibility

The toolkit's approach is binary string comparison — searching both binaries for the feature's symbols, enums, D-Bus properties, and QML components. The feature-claims-analysis.json document shows this methodology applied to X2D II vs X2D:

# Check if a feature's infrastructure exists in a different model's binary
# Example: Does X2D have E_CameraMode_Video?

strings camera-gui-software-x2d | grep -i "CameraMode_Video"
# No results = feature infrastructure absent

strings camera-gui-software-x2dii | grep -i "CameraMode_Video"
# E_CameraMode_Video, E_CameraMode_Image = present

Cross-model comparison matrix

For a specific mod, build a matrix of which required symbols/features exist in each target:

Required component X2D II X2D X1D II
capability_VideoMode (bit 3) Present Present Present (enabled)
E_CameraMode_Video Present (gated) Absent Present (active)
ExpModeSelector.qml Has Photo/Video toggle Photo only Has Photo/Video toggle
Video recording pipeline Infrastructure present, gate only No mode switching Fully active
Verdict Patchable Not feasible N/A (already works)

7. Automated Validation Pipeline

The mod_install.py tool validates a mod manifest against any firmware profile. Running it across multiple profiles produces a compatibility report:

# Validate one mod against all X2D II profiles
for profile in profiles/X2DII_100C_v*.json; do
  echo "=== $(basename $profile) ==="
  python tools/mod_install.py validate \
    mods/video-mode-restore.json "$profile" --json 2>/dev/null \
    | python -c "
import sys, json
d = json.load(sys.stdin)
status = 'OK' if d['compatible'] else 'FAIL'
issues = ', '.join(d['issues']) if d['issues'] else 'none'
print(f\"  {status}: {d['firmware']} ({len(d['steps'])} ops, issues: {issues})\")
"
done

What the validator checks

CheckHow it worksFailure mode
Firmware version match Compares target_firmware in manifest against profile's firmware filename and build string Blocker — wrong firmware
Model match Normalizes model names and compares Blocker — wrong camera
Stock hash verification Compares mod's declared stock_sha256 against profile's hash for that file Blocker — binary mismatch means patch offsets are wrong
Porting status Reads porting_status.{model_key} from manifest "not_started" is a blocker; "in_progress" is a warning
Technique warnings Binary ELF patches get a "version-locked" warning; dlsym gets "verify symbols" Advisory

8. Building a Version Compatibility Matrix

For a production-ready mod, build an explicit compatibility matrix in its manifest:

{
  "mod_id": "video-mode-restore",
  "firmware_versions": {
    "x2dii_1.3.18.1": {
      "stock_sha256": "8c5af67c...",
      "patched_sha256": "07f4d058..."
    },
    "x2dii_1.3.16.2": {
      "stock_sha256": "9fd63cd1...",
      "patched_sha256": "f8dc67c5..."
    }
  },
  "porting_status": {
    "x2d_ii": "verified",
    "x2d": "not_applicable",
    "x1d_ii": "not_started"
  }
}

Each firmware version entry carries its own stock and patched SHA-256, so the journal engine can verify integrity regardless of which version is installed. The porting_status map gives humans and tools a quick answer on cross-model feasibility.

9. Case Study: Video Mode Restore

The video-mode-restore mod illustrates the full porting analysis workflow:

Same model, different firmware versions

X2D II 1.3.16.2X2D II 1.3.18.1
Getter address 0x010aefc8 0x010aefc8
Redirect offset 0x010aefec 0x010aefec
Code cave 0x029cf4bc 0x029cf4bc
Instructions Identical sequence Identical sequence
Patch bytes Same 20 bytes Same 20 bytes
Verdict IDENTICAL_PATCH — same 20 bytes apply to both
Why this happens Minor firmware updates (1.3.16 to 1.3.18) typically fix bugs and add small features without recompiling core libraries from scratch. The linker places functions at the same addresses, and the code cave remains zero-filled. This is common within a minor version series.

Cross-model: X2D II vs X2D

ComponentX2D IIX2D
capability_VideoMode Bit 3 exists, not set by backend Bit 3 exists in enum
E_CameraMode_Video Present — the mode switch target Absent — only E_CameraMode_Image + _Max
Video QML UI Full ExpModeSelector with Photo/Video ExpModeSelector without Video option
Verdict Patchable (20-byte gate lift) NOT_APPLICABLE — the enum value to switch to doesn't exist

Setting capability_VideoMode on X2D would make the QML check pass, but the mode switch action (setCamera_mode(E_CameraMode_Video)) would fail because the enum value doesn't exist in the X2D binary. The entire video mode switching infrastructure was added for X2D II and never existed in X2D.

10. Porting Workflow Checklist

Use this when porting any mod to a new firmware version or camera model:

Phase 1: Profile comparison

  • Build or obtain the stock profile for the target firmware
  • Compare target file hashes: identical = apply as-is
  • If hashes differ, determine if it's the same model (re-derive) or different model (feasibility check)

Phase 2: Feasibility (cross-model only)

  • Search for all required symbols, enums, D-Bus properties, and QML components in the target binary
  • Build a component presence matrix (like section 6)
  • Determine tier: IDENTICAL_PATCH, SAME_TECHNIQUE, PARTIAL_PORT, NOT_FEASIBLE, NOT_APPLICABLE

Phase 3: Re-derivation (if hashes differ)

  • For binary patches: locate function, find cave, verify instructions, recompute offsets
  • For string patches: search for string in new binary (usually just an offset change)
  • For text mods: verify pattern matches in new version of the file

Phase 4: Manifest update

  • Add new firmware version entry with correct hashes
  • Update porting_status for the model
  • Update target_models and firmware_versions_human

Phase 5: Validation

  • Run mod_install.py validate against the new profile
  • Run the full test suite: python -m pytest tests/
  • If QEMU DevKit image available: boot and verify
  • If different model: note any limitations discovered during analysis
Key principle The stock profile is always the source of truth. Every porting decision starts and ends with comparing hashes against it. When in doubt, the profile settles it.
