Firmware Slot Flip

Emergency restore to stock firmware via A/B slot swap

Last resort only The slot flip abandons all mods on the current slot. Use normal restore_mod() or restore_all() first. This is for when files are corrupted, tampered, or normal restore has failed.

Background

A/B partition layout

X System cameras have two complete system partitions (slot 1 and slot 2). One is active, one is inactive. Official firmware updates always write the inactive slot, then flip to it on reboot. This means the inactive slot holds clean stock firmware from the last update.

Why this is safe

Mods write the active slot only. They never touch the inactive slot. So flipping to the inactive slot boots you into unmodified firmware — guaranteed, as long as no mod has written both slots.

Pre-flight checks

All three must pass before proceeding:

CheckCommandRequired state
No upgrade in progress unrd hbl_upgrading Empty / not set
No crash counter unrd crash_counter Empty / not set
Know current slot unrd slot_1.status_active
unrd slot_2.status_active		 Exactly one returns 1
If hbl_upgrading is set An official firmware update is mid-write to the other slot. The inactive slot may contain a half-written image. Do not flip — let the update finish first.
If crash_counter is set The verified-boot system is active. The bootloader is monitoring boot success. Interfering with slot state in this state risks a boot loop. Do not flip.

The flip sequence

Assuming slot 1 is active (your modded slot) and slot 2 is inactive (stock). Swap the numbers if reversed.

1

Reset crash counter

unrd crash_counter 0

Required before any slot status changes. Clears the verified-boot watchdog.

2

Activate the target slot

unrd slot_2.status_active 1

Tells the bootloader to boot slot 2 on next reboot.

3

Deactivate the current slot

unrd slot_1.status_active 0

Ensures only one slot is marked active.

4

Mark bootable

boot_control -m

Marks the newly-activated slot as successfully booted so the bootloader won't roll it back.

5

Reboot

reboot

Camera boots into stock firmware on the other slot.

Using the toolkit

The journal engine wraps this in a safe, pre-flighted operation:

# Pre-flight check (no side effects)
python tools/hbjournal.py slot-restore /blackbox/modjournal profile.json --dry-run

# Execute (requires confirmation)
python tools/hbjournal.py slot-restore /blackbox/modjournal profile.json

Or programmatically:

from journal import Journal, StockProfile, read_slot_info

j = Journal(journal_dir, system_root, profile, slot_info=read_slot_info())

# Check first
preflight = j.preflight_slot_restore()
if not preflight["viable"]:
    print(preflight["issues"])

# Execute
result = j.slot_restore(dry_run=False)
# Journal is marked FAILED — reboot to complete

What happens after

ItemState
Active slot Switched to the previously inactive slot (stock firmware)
Journal phase Marked FAILED — no further operations possible
Modded files Still on the old slot's partition, but inactive and not running
ADB keys Preserved — adb_keys lives on /blackbox, shared between slots
Next official update Will overwrite the old modded slot with clean firmware

What unrd and boot_control are

/sbin/unrd

Reads and writes non-volatile boot properties stored outside both system partitions. This is how the bootloader knows which slot to boot. Properties are key-value pairs persisted in a dedicated storage area.

boot_control

Android's A/B boot control HAL interface. The -m flag marks the current slot as "successfully booted." Without this, the bootloader may decide the slot failed to boot and roll back on the next reboot.
